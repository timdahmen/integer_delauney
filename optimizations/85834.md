# Performance Optimizations

As previously established, the memory boundaries between parts of the application tend to swallow the most
amount of time and require the most technically challenging workarounds. My focus was on working with some
of these boundaries.

## Working on the warm insert: partial_triangulate.

The *host* sections in the NVTX traces are of particular interest since they do not benefit from
the parallel processing capabilities of CUDA.

**Observations**:
- inc: compact registry (host)
The CPU does some more difficult mental gymnastics here:
1. Create a number vector ("remap") of the size of the old elements 
2. Create a vector ("compacted") the size of the stale objects and the ones to add
3. Then it iterates over all of the old elements and check for staleness every time
4. If *not* stale, save the index on the "compacted" vector to the "remap" vector and push that element
5. Append the new triangles to the "compacted" vector
6. Memory-move that vector to the triangle ref

This section becomes relevant later. The method rebuilds the lookup maps next
- inc: rebuild lookup maps (host)
1. The *tid* to triangle ref map is cleared 
2. Using the new triangles size, iterate through the newly created triangle vector 
3. Retrieve the triangles 
4. Pack them as a triplet so they can be used for the triangle ref map
5. Using the triangle triplet key, set the value (triangle index) for the refmap

Fundamentally, this solves the wrong problem. This should be using references instead of a map.
Granted, the map itself is using hashing, though, it is also reused in an acceptable manner. 
My goal was not to redesign the data layout here, but I found a few things I could immediately
address.

**Idea (rev 1)**:

This becomes slow at scale. A way to avoid having to to move a large amount of elements would be nice.
For that we could try to localize the data in-place.

1. Let's do away with the extra "compacted" map. "h_triangles_" is already a map so this should be acceptable.
2. Invert the control flow. If a triangle is stale, remap it instead
3. Directly erase the offending triplet, we already have the ref for it.
4. Create a direct remapping using stored offsets (in-place)
5. Resize the triangle map. Not ideal but saves some memory moving.
6. No need for remapping, the new triangles can just be done by size.

**Results**:   

Not ideal for the added complexity. Yes, it does some of the lifting at higher triangle counts, that's what
this was aimed at. This can be further improved by reducing the memory pressure / only transferring partial
memory maps to the GPU.

Tests were done at 1024x1024, 100k seed points    
**Before:**`Incremental warm (CUDA) 127.0ms`    
**After:** `Incremental warm (CUDA) 58.0ms`


## Working on the memory side of things: pre-allocated buffers

**Observations**:    
The GPU kernel spends most of its time idle vs warm (0.8ms vs 50-60ms). After consulting the NVIDIA CUDA documentation
it seemed like the correct thing would be to pin the host buffers so memcopy / moving would use a known pre-cached path.

In my specific case this turned out to be a trap, after some more instrumentation (curtesy of Claude) the results showed
something else. The GPU available to me is not connected with an optimal link-width and there seems to be no way for me
to change that dilemma. 

**Idea (rev 1)**:

Re-work some of the host-device transfers (where structural write / read patterns allow) to use CUDA host allocations.
These are very expensive to both maintain and create, but these should speed up memory transfers.

**Results**:

This may still have worked to some degree, I just don't have any means of testing it. The next idea would be to weigh
data transfer speeds to how fast the host could preempt the memory, potentially transferring less

**Idea (rev 2) and Results**:

A few things were tried
- Moving triangle map population to the warm branch, yields no results because its always updated so just moves the problem
- Control flow inversions didnt help, those got eaten by the extra allocation needed (1-2ms max)
- Using a stream to split buffer-read-write into a pipeline with events, turned out infeasible, CPU timing eats those, actually worse than before

## Working on assign_triangles_kernel

**Observations**:
One of the few areas of the program where significant improvements could still be made. The NVIDIA profiler shows a ton
of cache evictions around the `assign_triangles_kernel` function. Suspect this can be improved with localizing data or
removing data pressure (references).

**Idea (rev 1)**:

The nearby seeds in the area scan are run through twice, first for dedup and second for the compressed sparse row.
Somewhere around here the profiler complains about memory locality. I am guessing this is about the nearby array.
If the entire nearby scan is avoided (by folding it into containment test) then this avoids having to store said matches,
potentially fixing this issue and avoiding the memory latency.

**Results**:

Well, this turned out to be worse. GridTriangulation slowed down by about 20-30ms. 
Luckily I figured out why: We are now brute forcing every CSR run against every seed because these reappear. The
question then becomes if a (between csr) shared means of keeping track of these used ones is more efficient than 
preempting them. 

**Idea (rev2)**:

Introduce a history for these. This is more of a proof-of-concept at this stage, I am not too sure how well it
scales. The one thing it can't do is influence the result: This system is redundant, the brute-force approach works
so no matter how badly this goes, it can only improve things, hopefully beyond what the original had.
